2. The Hebrew deck, slide by slide

FACT agent_presentation/deck-he.pdf has 10 pages (PDF 1.7, produced by Firefox 155.0.1 / cairo 1.18.4 on 2026-09-15). Each page was rendered with PyMuPDF at 2400×1350 px and read in full. What the deck commits to that constrains an Obsidian decision

  • FACT Slide 3 states the storage boundary in one sentence: nothing is stored on the platform; retrieval and embeddings are the organisation-wide (IT) service's job.
  • FACT Slide 4 places the LLM Wiki on the user's Windows computer, reached by agents as an MCP server at 127.0.0.1, with the user approving each call. It is "built by agents" but held by the user.
  • FACT Slides 1, 2 and 10 make the LLM Wiki the flagship of the autonomous layer (the Deep Research analogue, the 2027 justification, "agents that improve the LLM Wiki").
  • FACT Slide 4's four zeros define the container: no network route, no inherited credentials, no packages installed at run time, nothing kept after deletion. Any GUI application inside the container is outside this design.
  • INFERENCE The deck never mentions a note-taking application, an editor, or a viewer for the wiki. It leaves the human side of the wiki (reading, curating, browsing, presenting it to a manager) unspecified. That is the gap an Obsidian decision fills.

3.6 What the architecture says about a tool such as Obsidian, before any audit

INFERENCE Three consequences follow directly from the directives above:

  1. The wiki lives on the user's computer and in plain files. The platform explicitly refuses to store it; the user "gets the results locally" and exposes them back to agents as a folder, a zip, or an MCP server at 127.0.0.1. A desktop application that edits a folder of Markdown files is architecturally inside the design, not beside it.
  2. Agents never see a GUI. They run in a network-less container with a curated command line. Whatever tool the humans use must produce files the agents can read and write with grep, sed, Python and Git, and must not require its own process to be present in the container.
  3. Retrieval is not this platform's job. The deck says so on slide 3. A knowledge tool's built-in search is therefore a desktop feature for humans, and an embedding index is either IT's service or nothing.

4.2 The protocol the agent speaks, and the agent identity

  • FACT The live protocol is streamed OpenAI Chat Completions (POST /v1/chat/completions, stream: true) plus vLLM's POST /tokenize for exact token counting and GET /v1/models for preflight (docker/config/settings.json:25-33,78-100; docker/tests/check_composition.py:103,128-145). Anthropic Messages and OpenAI Responses are served and probed on the backend but not used by the agent (README.md:634-647).
  • FACT kv_scope is a required top-level JSON body field, not a header, declared on six request models (the shared-prefix patch, lines 6486–6809). The engine gate require_kv_scope() returns HTTP 400 on every generation route when it is missing or whitespace-only. Patched Qwen Code writes it last on every request so no setting can override it (review diff lines 169329–169331). The main session uses its own session ID; a subagent uses the ID of the tool call that spawned it (patches/README.md:36-42).
  • FACT Semantics (docs/kv-user-count-and-agent-scope-design.md:10-30): an ID with no cached blocks may acquire any matching shared prefix (an implicit fork); once it has blocks it matches only data it acquired or computed. GPU and CPU tiers share one membership catalog. The ID gives cache accounting, "neither authentication nor a confidentiality boundary".
  • FACT Capacity is declared in user contexts, not bytes: --kv-cache-users 1 on the GPU and cpu_kv_cache_users: 1 in the offload connector (config/runtime-v1.sh:289,324-325). The host tier is an mmap in the container's /dev/shm, about 6.6 GB for one context, pre-faulted and page-locked; a cudaHostRegister failure now raises instead of warning, and readiness re-checks the logs for it (scripts/runtime-common.sh:958-998). Under pressure the host tier releases whole agents in LRU order, never the incoming one, and declines a store rather than evicting partially.
  • FACT Why the host tier exists, in the config's words: a foreground subagent competes for the one-context GPU pool, and "losing the few GDN state blocks collapses the whole GPU prefix hit … Offloading keeps those blocks in DDR5 and restores them by DMA" (config/runtime-v1.sh:303-309). Pages move as opaque int8 bytes at 24,832 B/token.
  • STATUS The identity and eviction rules are SOURCE-TESTED (544 scheduler, cache, geometry, protocol and tiering tests plus 30 input-stream tests in offline CPU containers) and the v26 image carrying them is built and reproduces; but the README still says image adoption is pending and no live GPU validation of kv_scope sharing or whole-agent eviction is recorded. All live prefix-cache measurements predate kv_scope.

4.7 What agent_service explicitly does not do

  • No capacity or placement decisions: "it cannot know it is not one worker behind a load balancer, so serving capacity and placement are governed above it" (README.md:8-11). No queue, no scheduler, no fairness, no authentication (loopback-only bind).
  • No MCP, hooks, skills, memory, workflows, web tools, UI, SSH, ttyd or browser; no retries, no fallbacks, no alternate client modes.
  • No waiting endpoint, callbacks or streaming progress; no second upload protocol; no host input mounts; no write-back to the caller's folder; no automatic pruning.
  • No batch-inference or DoubleWord-style job tiers, although the service itself already has the job shape: durable acceptance, then polling. The backend's /v1/chat/completions/batch exists but with --max-num-seqs 1 there is no parallelism, and the service does not use it.
  • A grep over both repositories finds no mention of "wiki", "knowledge base", "RAG", "Obsidian", "Kanban", "canvas", "vector" or "DoubleWord". Embeddings appear only as refusals ("callers cannot provide image embeddings"); no embedding route is served.

4.8 What this means for a Markdown vault, concretely

  1. In: ./run.sh /abs/vault /abs/prompt.txt zips the folder with zip -0 -ryq ., dotfiles and hidden directories included; .obsidian/, .git/, .canvas JSON files and Kanban notes arrive verbatim. Nothing in .obsidian/plugins/*.js runs unless the model chooses to execute it in the shell.
  2. Visibility: upstream Qwen Code's respectGitIgnore and respectQwenIgnore default to true and the sealed settings do not override them (INFERENCE from the upstream docs inside the review diff), so the structured tools may skip paths matched by the vault's .gitignore; the shell (rg, fd, cat) is unaffected.
  3. Reading: Markdown, JSON Canvas and Kanban files are plain text; read_file pages 32,768 bytes at a time; PDFs are text-only extraction (render scanned pages to PNG with pdftoppm to view them, 15 per request); JPEG or WebP attachments must be converted to 8-bit RGB PNG in /tmp first.
  4. Editing: edit, write_file or any shell program, under Landlock, only inside /workspace, /artifacts, /tmp, /qwen-runtime. Scratch indexes and databases belong in /tmp and are discarded.
  5. Out: the bundle's staged/ is the entire final vault, not a diff, with all mtimes zeroed. Syncing back into a live vault must compare content (rsync --checksum or git diff), not timestamps. Nothing persists between sessions; the wiki's state must live in the files.
  6. Scale: ~35–40 s per turn at long context, 400-turn default budget (2,000 ceiling), compaction at 180,347 tokens; the 1.55M-word corpus test has never completed, so a wiki pass must be sized in chunks the way the BSP team's real wiki (707 KB per document, ≤3 MB per category) already is.

Documentation drift noted by the pass: the backend README still calls v23 image adoption "pending" while v26 is pinned; one line says "eighteen" images against the 15-image cap; the Qwen Code patch now covers 799 paths against the "104" and "61" the two READMEs cite; the 2026-08-15 client audit says subagents "must not be the default" while the current sealed prompt says "Delegate generously"; the same audit says completed thinking is omitted while both READMEs now say historical reasoning is always preserved.

6.4 How much Hebrew evidence actually exists

  • FACT MTEB has no Hebrew benchmark. Hebrew appears only as a subset of multilingual tasks; inside MMTEB v2 it contributes to Belebele retrieval, MASSIVE intent, SIB200 clustering and bitext mining. Belebele has 900 questions per language and is near saturation for the top models (95–97). A model's MMTEB average therefore says little about Hebrew retrieval.
  • FACT Outside MTEB: the Hebrew Semantic Retrieval National Challenge (MAFAT / Israel National NLP Program, on Codabench, NDCG@20), where Dicta's neodictabert-bilingual-embed (768 dims, 4,096 context, CC-BY-4.0) reports 10th place in the private phase; and Sefaria's leaderboard, which covers Rabbinic rather than modern Hebrew.
  • INFERENCE The public signal cannot settle which model retrieves best over Hebrew and English engineering wikis. A 200–300-query gold set built from the real wikis is the only decisive test, and it is cheap.

6.5 Practical notes for the patched stack

  • vLLM serves embedders with --runner pooling; the client must prepend the Instruct: …\nQuery: prefix for Harrier, Octen and Qwen-style models.
  • Cap --max-model-len at the chunk size (2,048–8,192) rather than 32k; it saves memory and avoids the long-input chunked-prefill bug in PR #48214.
  • The 27B on a shared 96 GiB RTX PRO 6000 at FP8 (~26 GiB plus runtime) takes roughly a third of the card away from LLM weights and cache; its natural home is a dedicated card. The sub-1 GiB models cost nothing that matters.
  • Vectors are not portable between models; changing the embedder means re-indexing everything.

8.2 Laguna instead of Ornith

Not as a 1:1 replacement, and not for the LLM Wiki. Laguna has no vision tower. The deck promises 16-megapixel page conversion of PDFs, image labelling and object grounding on the same served model (slides 2, 3, 9), and the sandbox contract makes "render the page to PNG and look at it" the only way to read a scanned datasheet. A text-only frontier model breaks all three. On the benchmarks Poolside itself publishes, S 2.1 sits at the Ornith 35B-A3B level (Terminal-Bench 2.1 70.2 vs 67.8) and 16 points under Ornith 397B, with nothing published on long context, which is the entire basis of the 397B-for-the-wiki argument.
Where Laguna S 2.1 is genuinely attractive. It is the only candidate with zero PRC lineage, so it survives a stricter reading of the rule than "wink wink". Its 8 KV heads fit TP=8 with no replication, so it reaches roughly 226–256 DGX seats on the engine as it is, without the TurboQuant DCP work the deck's 339 depends on. Its checkpoint is small (about 62 GiB NVFP4) and it fits one RTX PRO 6000 with two or three 256K seats. If the policy owner ever demands "no Chinese base at all", Laguna is the answer for the code-agent workload, paired with a separate vision-capable model for pages and images, and the deck's capacity slide must be recomputed. That is a different architecture from the one drawn.

Two things to do before deciding: run the K8V4-versus-FP8 A/B on S 2.1 in the patched engine on the external card (nobody has published one), and read the current NVFP4 index of poolside/Laguna-S-2.1-NVFP4 on a machine that can reach Hugging Face, because the two revisions differ by 30 GB.

8.3 An embedding model

Do not add one to the platform for the LLM Wiki. The deck says so on slide 3, the prompt file says so twice, and the wiki mechanism (a long-context agent that reweighs every chunk against everything already written) is the deliberate alternative to retrieval. Bolting a vector index onto the sandbox would also require the one thing the four zeros forbid: persistent storage owned by the platform.
If the boundary is ever reversed deliberately, the order is: Harrier-27B when a card can be dedicated to it (clean Gemma lineage, MIT, first on MMTEB, Hebrew listed, but ~26 GiB at FP8 with no official FP8 checkpoint and no public vLLM run of the 27B); Octen-8B only with a written policy decision, because it is the Chinese embedder re-tuned rather than a base model continued; multilingual-e5-large-instruct as the sub-1-GiB default for Hebrew-heavy content. In every case build the 200-query gold set from the real wikis first; Belebele's 900 questions are the only public Hebrew retrieval signal and the top models have saturated it.

The premise of the question deserves one correction: the "Microsoft 27B" is not a Qwen retrain but a Gemma retrain, and the "retrained by Taiwanese or Singaporeans" model is Octen, whose founder ran AI search at Alibaba Cloud. Neither is what the phrasing assumed, and the second is a weaker provenance story than Ornith's.
